## 1. The 60-second mental model

Leon Bookings is a **single-process, self-hosted planner** for apartments/studios
and cars/bikes. One Spring Boot process serves a React SPA, exposes a versioned
JSON API, and stores everything in a local SQLite file. There is no multi-tenancy,
no external service, and no built-in TLS.

```text
Browser ──same-origin /api/v1/*──▶ Spring MVC controllers
                                     │  Spring Security (session + CSRF, roles)
                                     ▼
                                  services (booking rules, money, reports, licensing)
                                     ▼
                            Spring Data JPA / repositories
                                     ▼
                                   SQLite (bookings.db)
```

Alternative entry points:

- `./mvnw generate-resources spring-boot:run` — development server (dev profile).
- `docker compose up --build -d` — production profile in a container, DB in a
  named volume.
- `install/package.sh|ps1` — desktop portable app / installer with bundled JRE.
- `java -jar ... db backup|restore` — **offline CLI dispatched before Spring starts**.

Sources: `README.md:8-48`, `docs/application-deep-dive.md:39-55`,
`src/main/java/com/leonsoft/Application.java:10-19`.

## 4. Architecture and request flow

### Layers and boundaries

1. `api/` controllers validate DTOs (`BookingRequest`, etc.) and map to entities.
2. `services/` own business rules: derived nights and balance, overlap checks,
   active-resource checks, audit records, licensing, report rendering.
3. `repositories/` are Spring Data interfaces over JPA entities.
4. `config/SecurityConfig` is **deny-by-default** (`anyRequest().denyAll()`),
   with explicit role rules and cookie CSRF; `LicenseEnforcementFilter` is added
   after `AnonymousAuthenticationFilter`.
5. Errors are rendered as JSON for API requests (`CustomErrorHandler`,
   `LicenseEnforcementFilter`, `SecurityConfig`).

### Runtime path for a booking write

`frontend/src/bookingApi.js` → `POST /api/v1/booking/save` (+ CSRF header from
`/api/v1/csrf`) → `BookingsRestController` → `BookingsService.create` →
`saveWithNormalizedValues` (resource existence/active, overlap policy, nights,
money normalization, server-calculated `rentalTax` and `balance`) → repository →
`AuditService` record.

Sources: `src/main/java/com/leonsoft/services/BookingsService.java:53-143`,
`frontend/src/bookingApi.js:17-57,104-131`.

### Frontend routing and state

Query-parameter routing in `frontend/src/main.jsx:20-34,50-118`:

| URL | Screen |
|---|---|
| `/?type=rooms` / `/?type=cars` | `BookingPage` (default) |
| `?page=reports` | `ReportsPage` |
| `?page=resources` | `ResourcesPage` (admin) |
| `?page=users` | `UserManagement` (admin) |

On startup the SPA loads current user (`/api/v1/users/me`) and license status;
if not activated it renders `LicenseGate` instead of any screen. Theme and
language are browser-local preferences. CSRF token is cached in module state and
reset on logout.

### Frontend structure and data flow

```text
AppRouter (main.jsx)
 ├─ LanguageProvider / loading splash
 ├─ LicenseGate (blocks every screen until activated)
 └─ lazy page by ?page
     ├─ BookingPage → BookingForm + two BookingTimeline panels
     ├─ ReportsPage
     ├─ ResourcesPage
     └─ UserManagement
```

- There is no React Router or state library. Navigation is query-string based,
  with delegated same-origin anchor handling, `popstate`, and a `key` on
  `location.search` to remount pages when the query changes
  (`frontend/src/main.jsx:20-48,71-91,114`).
- All API calls go through `frontend/src/bookingApi.js:17-57`: same-origin
  cookies, `Accept-Language` from localStorage, 401 redirect to `/login`, and a
  module-level CSRF token cache. `frontend/src/usersApi.js` duplicates some user
  wrappers.
- `frontend/src/bookingLogic.js` owns date conversion, nights, client-side
  balance/subtotal, overlap checks, payload mapping, and safe timeline labels.
  `BookingForm.jsx` also computes rental tax from the selected resource; the
  backend nevertheless re-derives nights/tax/balance on save.
- Reports have a fourth implementation in the browser: `reportLogic.js` includes
  bookings by **arrival date** and excludes cancelled bookings from financial
  totals, while CSV is generated in `ReportsPage.jsx` with hardcoded English
  headers.
- `vis-timeline` is loaded as a global script from `public/js/`; there are two
  hand-maintained HTML shells (`frontend/index.html` for Vite dev and
  `public/index.html` for production) and two global stylesheets.
- Vite emits JS chunks into gitignored `src/main/resources/public/react-assets/`
  with fixed names, so release correctness depends on regenerating assets via
  Maven or `npm run build`; `emptyOutDir:false` can leave stale chunks.

Sources: `frontend/src/main.jsx`, `frontend/src/bookingApi.js`,
`frontend/src/bookingLogic.js`, `frontend/src/reportLogic.js`,
`frontend/vite.config.js:5-7,29-47`.

### Domain model (important details)

- `Booking`: `startDate`/`endDate` as `LocalDate`, `numOfNights` derived,
  money fields stored as **integer cents** via `MoneyCentsConverter`, status
  `active|paid|cancelled`, `resourceId` is the stable FK-like value and
  `resourceName` is display-only. Balance = `charge - received - commission - rentalTax`.
- `BookingResource`: `rooms|cars`, name, active flag, per-night `rentalTaxPerNight`,
  registration/address/tax metadata.
- `User`: implements Spring Security `UserDetails`, roles `ADMIN`, `OPERATOR`,
  `GUEST`; BCrypt password hashes.
- `AppInstallation` / `AppLicense` / `Customer`: one install ID, one active
  license, one licensed customer record.
- `AuditLog`: created by `AuditService` for booking/customer/license/user actions.
- Migrations show the evolution: status constraint, integer-cent money, ISO date
  normalization, `room` → `resource_id`, rental tax, compliance fields,
  licensing, default-password hash, audit log.

## 5. Security, licensing, and operations

### Roles (backend is authoritative)

| Capability | ADMIN | OPERATOR | GUEST |
|---|:---:|:---:|:---:|
| View bookings/resources | yes | yes | yes |
| Create/update/delete bookings | yes | yes | no |
| Reports + PDF/CSV export | yes | yes | no |
| Manage resources | yes | no | no |
| Manage users | yes | no | no |
| License/customer activation | yes | no | no |
| Support bundle / app info | yes | yes | yes |
| Actuator health/info | yes | no | no |

Deny-by-default plus last-active ADMIN/OPERATOR protections in `UserRestController`.

### License flow

1. `LicenseService.getOrCreateInstallId()` creates/persists a UUID for the install.
2. ADMIN sees it in the UI and obtains a signed key built as
   `base64url(JSON payload).base64url(Ed25519 signature)` (`tools/LicenseSigner.java`).
3. `POST /api/v1/license/activate` → `LicenseVerifier` checks signature with
   `APP_LICENSE_PUBLIC_KEY` (dev key is fallback), product name, install ID, and
   customer name → customer upsert → license row marked `ACTIVE` → in-memory
   `activatedCache = true` → effective immediately.
4. `LicenseEnforcementFilter` blocks normal `/api/v1/*` traffic until activated,
   while permitting login, static assets, SPA shell, CSRF, `/users/me`,
   license status, and admin license/customer APIs.
5. `app.license.bypass=true` disables the gate; **dev default**, prod sets false.

Sources: `src/main/java/com/leonsoft/services/LicenseService.java:51-132`,
`services/licensing/LicenseVerifier.java:35-84`,
`config/LicenseEnforcementFilter.java`, `README.md:262-286`.

### Reports — three implementations that do not fully agree

- **HTML** (`GET /api/v1/booking/report`): `BookingReportService.report()` filters
  bookings fully contained in `[fromDate, toDate]`, renders escaped HTML with
  `BookingsHtmlTemplate`, and accumulates totals with `double` **including
  cancelled bookings**. Its totals table currently has 7 headers but 8 cells
  after the `rentalSubTotal` column was added.
- **PDF** (`GET /api/v1/booking/export/pdf`): `exportReportToPDF()` filters by
  resource type but **not by the requested dates** (the dates only appear in the
  title). Summaries exclude cancelled bookings, the detail table lists them, and
  the embedded DejaVu font supports Greek text.
- **CSV**: generated entirely in the browser (`ReportsPage.jsx`), so its filters,
  formatting, and totals are independent of the backend implementations.

Sources: `services/BookingReportService.java:48-120`,
`services/BookingsHtmlTemplate.java:69-165`, `services/BookingsPDFExporter.java:82-185`.

### DB and backups

- SQLite file is local (default `./bookings.db`, `APP_DB_URL` overrides). Do not
  share a live DB over a network share; only one process should use it.
- Only V1-baselined/current schemas are supported; pre-V1 databases must be
  exported/reimported or upgraded outside the supported path (owner decision in §11).
- `java -jar <jar> db backup [--encrypt] [--database …] [--output …]` and
  `db restore …` are offline, validate SQLite integrity, refuse overwrite, and
  write a pre-restore backup. Encrypted backups use AES-256-GCM with PBKDF2 and
  an interactive passphrase; no recovery if lost.
- Upgrade procedure: stop app → encrypted backup → upgrade → smoke test login,
  license, booking CRUD, report export → keep old backup until verified.

| Variable | Purpose | Default / notes |
|---|---|---|
| `APP_ADMIN_USERNAME/PASSWORD`, `APP_OPERATOR_*`, `APP_GUEST_*` | Seed accounts created only when missing | Passwords ≥ 12 chars; built-in dev password `1qaz2wsx3edc` is rejected in prod. |

| `BOOKING_AVAILABILITY_ROOMS_PREVENT_OVERLAP`, `..._CARS_...` | Overlap enforcement per resource type | Both default `true`; read via `/api/v1/settings/availability`. |
| `APP_LICENSE_PUBLIC_KEY` | Production Ed25519 X.509 public key (base64) | Dev key fallback otherwise; keep private key outside repo. |
| `APP_LICENSE_BYPASS` | Disable license gate (dev/test only) | `false` globally, `true` in dev profile. |
| `APP_DIAGNOSTICS_LOG_FILE`, `LOGGING_FILE_NAME` | Log file location | `/data/application.log` in Compose. |
| `APP_DEPLOYMENT_TYPE` | `standalone|desktop|docker` | Validated at startup by `ApplicationConfigurationValidator`. |
| `VITE_BOOKING_SAVE_MODE` | Frontend build-time default create/edit | `create` when unset; session override checkbox exists. |

`.env.example` is the template for Docker; never commit a real `.env`.

**Important Docker caveat:** `compose.yaml:8-20` forwards only the six seed-account
variables plus `APP_DB_URL`, `APP_DEPLOYMENT_TYPE`, `APP_DIAGNOSTICS_LOG_FILE`,
`LOGGING_FILE_NAME`, `SPRING_PROFILES_ACTIVE`, and `SERVER_ADDRESS`. Setting
`APP_LICENSE_PUBLIC_KEY`, `APP_LICENSE_BYPASS`, or `BOOKING_AVAILABILITY_*` in
`.env` does **not** reach the container. In particular, a Docker deployment that
expects a production public key will silently fall back to the embedded dev key.

Desktop launcher details (`install/desktop-launcher/.../DesktopLauncher.java`):
prompts for admin credentials (12–72 UTF-8 bytes), sets `APP_DB_URL` to
`jdbc:sqlite:<cwd>/bookings.db`, `APP_DEPLOYMENT_TYPE=desktop`, default loopback
bind, and stops the app when Enter is pressed. Logs go to OS-specific data dirs.

    `fetchMe()` in `BookingPage` each load the current user; `UserManagement.jsx`
    hardcodes `isAdmin={true}` and relies entirely on backend 403s for gating.
31. **Report filters diverge**: browser `reportLogic.js` filters by arrival date,
    backend HTML uses full containment, backend PDF ignores dates, and client CSV
    has its own totals and hardcoded headers (with no spreadsheet formula guard).
32. **Frontend build/asset fragility**: two hand-maintained `index.html` files,
    Vite output under a source directory with non-hashed chunk names, and no
    tests for `BookingPage`, `BookingForm`, `BookingTimeline`, routing, or real
    i18n rendering.
33. **Theme/language failure modes differ**: invalid persisted theme values throw
    (`frontend/src/theme.js`), while invalid language values silently fall back.
